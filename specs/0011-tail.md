# 0011 `bforge tail`

Status: accepted (28 October 2026). Implements the engine half of S8: F1.4.x and
F3.x wired into one read path.

## Problem

Framing and dissection both existed and nothing called them. A recorder writes raw
chunks; the decoder was reachable only from tests. Until one command takes a port,
frames the bytes and decodes the frames, neither feature is real, and the window
has no path to consume.

## Scope

`bforge tail`, the framing and dissector settings in `.bforge.toml`, and the rows it
prints. Not in this stage: the viewport that draws rows (D-01), per-byte timestamps
(D-47), checksum status in a row (D-41), and recording at the same time as tailing.

## Behavior

1. `tail` starts one pipeline per selected port, exactly like `record`, and never
   writes a vault.
2. Each port gets a byte machine built from its `framing` table. All six modes are
   available, and a mode that needs settings refuses to start without them.
3. The machine's clock is the chunk timestamp, passed before the chunk's bytes, so
   an idle-gap port flushes a frame when the transport was silent.
4. A port with a `dissector = { type = "c_header", file, root_struct }` entry has
   its header parsed and compiled at start. A missing file or an unknown struct is
   reported before the first byte arrives.
5. Each completed frame becomes one row: port, timestamp, delta, length, hex
   preview, text preview when the frame is mostly printable, the protocol tag, and
   the flattened field tree with byte offsets.
6. A frame that matches the schema but cannot be decoded keeps its row and carries
   `decode_error`, so a short frame is visible rather than dropped.
7. `--fields` prints the tree under each row; `--json` prints one JSON object per
   row, which is the shape the window will consume.
8. `--duration` bounds the run; without it, Enter stops.

## Data

Rows:

```text
TailRow { port, timestamp_us, delta_us, len, hex, text, protocol, fields, decode_error }
FieldRow { name, offset, len, value }
```

New `.bforge.toml` keys under `framing`: `sync` (1 to 8 hex bytes), `length_offset`,
`length_width` (`u8`, `u16_le`, `u16_be`, `u32_le`), `length_adjust`, `idle_gap_us`,
and `max_frame` (8 to 1048576, default 64 KiB). Validation names each missing or
malformed setting by path before a port is opened.

## Measured

28 October 2026. Hardware, ESP32-C3 on COM8, 115 200 baud, delimiter `0x0D`
because the sketch ends its lines with a carriage return:

```text
$ bforge tail -c esp32c3.toml --duration 3s
tailing 1 port(s) for 3.0 s, press Enter to stop
     0.000s +      0us esp32         21B                      t1008ED0FF62220800000
     0.000s +      0us esp32         26B                      T18ECFF008200E0002FFE6FE00
```

Software, through the same path with a COBS stream and the `imu_packet.h` fixture:
two frames decoded to `sync=43605 version=3 flags=5 channel=18 v_batt_mv=8190
gyro_z=-0.042`, and the second frame to `version=4`.

The first run of the hardware demo produced zero frames because the delimiter was
`0x0A` and the sketch sends `0x0D`. That is the tool telling the truth about a
configuration, not a framing bug.

## Known limit

Every frame in one slab carries the slab's timestamp, so a burst that arrives in a
single read shows `+0us` for all its frames. Per-byte timestamps need the baud
rate, and that is D-47.

## Test

```sh
cargo test -p bforge-core --test tail
cargo test -p bforge-core --test config_validation
cargo test -p bforge-cli
```

Six tail tests: a COBS port decoded through its header, a delimiter port with no
dissector, a sync-word port, an unknown port named, a bad framing setting refused
by both the validator and the builder, and a missing header file named. Six new
validation tests cover the framing settings and the frame limit. Two new CLI tests
cover a missing `-c` and a port that cannot be bound.
