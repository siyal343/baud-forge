# 03 — Conventions

This repository has a voice and a discipline. Match them; a change that ignores them will read as
foreign even when the code is right.

## Writing

The user's standing instruction, in force for chat, documents, commit messages and code comments:

- **Simplified Technical English, about 80% strict.** Short sentences: 25 words maximum for a
  description, 20 for an instruction.
- Active voice, simple present tense, one word for one meaning. No contractions, idioms or slang.
- Start an instruction with the verb. Use "must" for a requirement, "can" for a possibility,
  "may" for a permission.
- Use a vertical list for three or more items.
- Keep noun groups to three words or less.

Flavour of the existing prose, which you should copy rather than invent around:

> "The timeline dragged. To watch a recording pass, a person had to hold the slider and move it
> by hand, which is not what a DVR does."

The house habit is a **plain statement of what was wrong**, then what changed, then a measurement
or a test. Not "this PR improves X". No marketing adjectives.

## Commit messages

Format: one imperative subject line under about 70 characters, no trailing period, no `feat:` or
`fix:` prefixes. Then a body of short paragraphs and lists. The body says what was wrong, what
changed, how it was verified, and what was recorded as a result.

Real example (`30d1cf9`):

```text
Walk a vault forward instead of seeking to every payload

The reader seeks twice per record: once for the header, once for the payload. That is the right
shape for a scrubber, which jumps, and the wrong one for a whole-file pass, which does not.

LogReader::for_each moves the cursor with the file ... CSV 12.0 s to 5.5 s ... All three outputs
are byte-identical to the old ones, checked with cmp rather than by eye.

290 tests. D-110 closed; the reader still seeks for a window, because that is what a jump is.
```

Rules:

- End with the test count and the deferred entries you closed or opened.
- If you found a bug while writing the test, say so. It has happened four times here and the
  commit messages say it.
- Never claim a hardware result you did not run. Write "a test with a mock, because this machine
  has no serial port" instead.

## Specs

One file per feature, `specs/NNNN-<title>.md`, numbered from 0002 onward. The format is in
`specs/README.md`; the sections that appear in every recent one:

```text
# NNNN Title

Status: accepted (<date>). Closes D-nn.

## Problem        what was wrong, in plain words
## Scope          what this covers, and what it explicitly does not
## Behavior       numbered rules a reader can check
## Measured       the numbers, with how they were taken            (when there are numbers)
## Test           the test names and the command to run them
## Limits, recorded   what is still not true, and the deferred id
```

History is not rewritten. An accepted spec stays as written; a later change gets its own spec or
an entry in `DEFERRED.md`. `specs/0017-native-packs.md` still describes three packs, and
`specs/0047` and `specs/0048` add the other two.

## Deferred discipline

`DEFERRED.md` is the memory of the project. Every entry has an ID, a reason, the condition that
brings it back, and the consequence of leaving it.

- Open an entry when you leave something undone, or when you discover a limit while building.
- Close it by moving the row to **Closed** with the spec and commit that closed it.
- The ID is referenced from commits, specs and `NEXT.md`. Do not renumber.

The habit that has served this project best: when you create a gap while finishing something
else, write it down in the same commit. `D-113` existed for four minutes before the next commit
closed it; that is the right level of ceremony.

## Code

- Rust 2024 edition, `cargo fmt`, `cargo clippy --all-targets -D warnings` clean. No exceptions.
- Errors are enums with `Display`. Messages read as sentences: `"field `apid` needs 2 bytes but
  the frame has 0"`.
- Doc comments explain **why**, in one or two lines, at the seam or the trick — not what the
  line does. Look at `session.rs::forward`, `pipeline.rs::set_pins_one`,
  `export.rs::finish_block` for the register.
- Comments that record a shortcut use the form `shortcut: <limit>, <when to upgrade>`.
- Public items have doc comments because this project publishes its reasoning, not because a
  linter asks.
- No `unwrap()` outside tests, except where the invariant is local and visible in the same
  function (`try_into().unwrap()` after a length check).
- Name things after the domain: frame, chunk, slab, vault, port, trace, lane, rail, rails, pulse.

## Tests

- One behaviour per test, named as a sentence: `a_pulse_clears_what_it_set`,
  `an_unknown_message_keeps_its_id_and_its_bytes`.
- Fixtures are hand-built from the specification, never generated by the code under test. A pack
  tested against its own encoder proves nothing.
- Where a platform makes a behaviour untestable here, say so in the test's comment and in the
  spec's limits.
- Integration tests live in `crates/<crate>/tests/` and drive the public interface; unit tests
  live beside the code for parsers and edge cases.

## Documents

| Document | When it changes |
| --- | --- |
| `README.md` | Feature list and status line, when a stage lands |
| `STATUS.md` | At a stage end, with new numbers |
| `NEXT.md` | When an item is finished or a new priority appears |
| `DEFERRED.md` | Every commit that leaves a gap or closes one |
| `RELEASE-NOTES.md` | At a release, one section per version |
| `PLAN.md` | Only the header and the pointer to `NEXT.md` |
| `handoff/` | When the architecture or the traps change |

## Things this project does not do

- No emoji in code, commits or documents.
- No badge walls or marketing language in the README.
- No feature without a user-visible surface, unless its spec says why.
- No dependency for a few lines. The dependency list is short on purpose: `rustyline`, `rfd`,
  `tauri`, `serde`, `toml`, `mlua`, `object`, `object`/`gimli`, `memmap2` where it earns its place.
- No silent broadening of scope. If a fix grows, say so in the commit and the spec.
